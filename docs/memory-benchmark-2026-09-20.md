# MyClip Memory Benchmark 调研与实测

评测日期：2026-09-20。范围：按本轮确认，完成本地召回评测，解释与业界最终问答成绩的区别。

## 哪些 Benchmark 值得看

| Benchmark | 主要测什么 | 常见成绩口径 | 对 MyClip 的价值 |
|---|---|---|---|
| [LoCoMo](https://github.com/snap-research/locomo) | 跨多次对话的事实、时间、多跳推理与拒答 | 原始实现的答案 F1；厂商也使用 LLM judge，因此同名分数不一定可比 | 适合快速建立基础记忆召回基线；本轮已接入 |
| [LongMemEval](https://github.com/xiaowu0162/LongMemEval) | 信息提取、跨会话推理、知识更新、时间推理、拒答；500 题 | 官方最终回答二元正确率；另有会话/发言级检索指标 | 最适合近期持续回归；本轮使用完整 S cleaned 数据 |
| [BEAM](https://github.com/mohammadtavakoli78/BEAM) | 从 128K 到 10M token 的长历史，包含冲突消解、事件排序等十类能力 | 问答评分，按能力与历史规模拆分 | 适合数据增长后的质量与规模测试，现阶段优先级低于前两项 |
| [MemoryAgentBench](https://github.com/HUST-AI-HYZ/MemoryAgentBench) | 准确检索、测试时学习、长程理解、冲突消解 | 按任务报告对应的准确率或生成指标 | 适合验证增量写入、遗忘与更新是否正确 |
| [PersonaMem / PersonaMem-v2](https://github.com/bowen-upenn/PersonaMem-v2) | 从隐含信息学习用户偏好，跟踪偏好变化并个性化回答 | 个性化回答的任务评分 | 当 Profile 与个性化建议成为重点时采用 |
| [LongMemEval-V2](https://github.com/xiaowu0162/LongMemEval-V2) | 带截图的网页 Agent 历史，涵盖状态、操作流程、环境陷阱 | 固定 reader 的回答准确率、查询延迟；榜单使用准确率与延迟的综合增益 | 从输入形态看更接近 MyClip；适合后续完整截图记忆链路评测 |

这里的优先级是针对 MyClip 的判断，不是 Benchmark 的权威排名。LongMemEval-V2 是另一个任务设置，不能把 V1 分数移到 V2；作者当前页面的提交榜仍显示待发布条目。[V2 官方评测与榜单说明](https://xiaowu0162.github.io/longmemeval-v2/)

## 业界实际采用什么

- **Mem0** 公开评测覆盖 LoCoMo、LongMemEval、BEAM；它的评测流程包含记忆写入、检索、答案模型、评审模型。[官方评测仓库](https://github.com/mem0ai/memory-benchmarks)
- **Zep** 公开 LoCoMo、LongMemEval 的准确率、检索延迟和上下文 token 数，其当前说明使用 GPT-5.4 作为 reader 和 judge。[官方研究页](https://www.getzep.com/research/)
- **Hindsight** 的论文报告 LoCoMo 和 LongMemEval；另外维护持续更新的多基准结果页。[论文](https://arxiv.org/abs/2512.12818)、[结果页](https://benchmarks.hindsight.vectorize.io/)
- **Letta** 曾以文件系统工具运行 LoCoMo，说明“用文件维护记忆”也可以进入此类端到端评测。[官方实验说明](https://www.letta.com/blog/benchmarking-ai-agent-memory/)

最有价值的指标组合是：**最终回答正确率 + 全部证据命中率 + 延迟 + 上下文 token / 模型成本**。MyClip 还应增加来源准确率、事件时间准确率、旧事实被错误当成现状的比例。只看命中过一个片段或只看最终正确率，都无法定位是哪一层出了问题。

## 本轮测试口径

从当前工作区编译 Release 版 `myclip-mcp`，以真实 MCP 请求执行检索。数据来自固定版本的公开数据集，每个会话保存成 Markdown，每个对话或题目使用独立临时库。问题、答案、证据标签、预生成总结均不参与记忆构建。

每题将问题原文直接传给 `search_memories`，只搜索一次，最多返回 20 个文件；另外统计前 5 个文件的表现。没有 Agent 查询改写、继续读文件或生成答案。这测的是**当前检索器在原始会话 Markdown 上的单次召回能力**，不是生产中的“截图 → OCR → Agent 维护文件 → 多轮查询 → 回答”完整体验。

LoCoMo 全量 1,986 题中，446 道 adversarial 题不适用正证据召回，另有 4 道无证据和 4 道证据标注无效；参与召回计分的是 1,532 题。LongMemEval 全量 500 题中，30 道 abstention 题不参与正证据召回，计分 470 题。拒答类问题仍执行搜索，但本轮没有答案模型，不能评价是否正确拒答。

文件级指标对标准证据会话去重；片段级指标检查返回文本是否包含完整的标准证据发言。后者比较严格，长发言没有全部返回不等于答案一定错误。也不能把搜到正确文件视为 Agent 已经读到了全部证据。精确定义、数据校验值和重跑命令见 [评测协议](memory-benchmark-protocol.md)。

## 实测结果

**全部 2,486 道问题已执行搜索；可计分证据召回题为 2,002 道。** 结果如下：

| 数据集 | 可计分题数 | 文件召回率 @5 | 全部证据文件命中 @5 | 完整证据发言覆盖 @5 |
|---|---:|---:|---:|---:|
| LoCoMo | 1532 | 83.0% | 77.5% | 55.2% |
| LongMemEval-S cleaned | 470 | 91.2% | 83.4% | 64.7% |

`@5` 表示只看排名前五的文件及其返回片段。“全部证据文件命中”按题计分；“发言覆盖”先计算每题覆盖的证据发言比例，再取平均。两者分母不同。

| 数据集 | 文件召回率 @20 | 全部证据文件命中 @20 | 完整证据发言覆盖 @20 | MRR@20 |
|---|---:|---:|---:|---:|
| LoCoMo | 97.0% | 94.4% | 61.7% | 0.7497 |
| LongMemEval-S cleaned | 97.9% | 95.5% | 67.8% | 0.9108 |

LoCoMo 每个对话只有 19–32 个会话文件，LongMemEval 每题有 38–62 个会话文件，此外各有三个根文件。前 20 已覆盖很大一部分候选集。因此接近 97% 的文件召回率不代表接近 97% 的问答正确率，更不是行业领先的证据。随机取五个文件的期望文件召回率分别是 16.6%, 9.9%；这里的随机值是数学参照，不是另一套产品的实测成绩。

### LoCoMo 分类结果

| 类型 | 可计分题数 | 全部证据文件命中 @5 | 完整证据发言覆盖 @5 |
|---|---:|---:|---:|
| 多跳 | 279 | 26.9% | 25.8% |
| 开放域 | 92 | 47.8% | 27.3% |
| 单跳 | 840 | 95.0% | 62.8% |
| 时间 | 321 | 84.4% | 68.8% |

### LongMemEval-S cleaned 分类结果

| 类型 | 可计分题数 | 全部证据文件命中 @5 | 完整证据发言覆盖 @5 |
|---|---:|---:|---:|
| 知识更新 | 72 | 95.8% | 83.8% |
| 跨会话 | 121 | 66.1% | 58.2% |
| 单会话：助手内容 | 56 | 100.0% | 19.6% |
| 单会话：偏好 | 30 | 83.3% | 48.9% |
| 单会话：用户事实 | 64 | 100.0% | 81.2% |
| 时间推理 | 127 | 77.2% | 75.4% |

时间推理、知识更新分类的数值仍然只是证据召回；本轮没有判断日期推理、事实更新或最终回答是否正确。LongMemEval 的证据发言中有 18 条超过 1,600 个 Python 字符，另有发言跨多个段落；完整发言覆盖是保守指标，尤其不能把“助手内容”一栏的低覆盖率直接解读成低回答正确率。

### 从实测能确定的短板

1. **跨会话证据汇集明显弱于单事实查找。** LoCoMo 单跳题前五找齐证据文件为 95.0%，多跳题只有 26.9%；LongMemEval 跨会话题为 66.1%。这支持优先验证问题拆解和多次有针对性的检索。
2. **候选文件和交付片段之间存在差距。** LoCoMo 有 415 题已经在前五找齐证据文件，但返回片段仍未完整覆盖全部标准证据发言。其所有标准证据发言都短于 455 字符，无法归因于 1,600 字符上限。把结果扩到前二十，整体发言覆盖也只从 55.2% 升到 61.7%；值得检查段落排序、相邻上下文和继续读取策略。
3. **词形和语义表达不同会造成漏召回。** 例如询问 Caroline 研究了什么，证据使用 Researching，而正确文件排到第 19；询问看过几位医生时，记录使用 Dr.、physician、dermatologist，三个标准证据文件均未进入前二十。它们是诊断案例，不能据此单独估计所有同义表达的错误率。
4. **本轮对 Agent 的评价有限。** MCP 接口明确接受关键词；本轮直接输入自然语言问题，也没有生成主题式 Wiki 记忆。Agent 改写查询、维护更清晰的文件和追加读取都有可能改变结果，需在下一层统一预算验证。

- 评测脚本 8 项测试通过，包括真实 MCP 导入、答案标签不进入记忆、错误证据不被悄悄丢弃、跨片段证据计分、换行符完整性。

## 如何理解与业界的差距

本轮可以定位召回短板，**还不能给出 MyClip 的业界名次**。原因是计分对象不同，而不是缺少一个排序公式。

举例：Hindsight 在 2025-12 论文中报告 LongMemEval 91.4%；Zep 当前研究页报告 LongMemEval 90.2%（451/500）。这些是包含模型回答的结果，协议与模型也不相同。它们不能与本轮“某比例的证据文件进入前五”直接相减；更不能据此宣布 MyClip 领先或落后几名。[Hindsight 论文](https://arxiv.org/abs/2512.12818)、[Zep 方法说明](https://www.getzep.com/research/)

完整比较需要给 MyClip 和候选方案同样的原始数据，固定生成/回答/评审模型、上下文预算和检索调用预算，保留失败与拒答题，再测全部问题。Hindsight 的公开分数也不能直接作为把它接进 MyClip 后的预期收益；Zep 托管产品成绩不等于单独引入 Graphiti 的成绩。

## 建议的后续顺序

1. 将本轮数据与脚本保留为可重复基线。用独立开发集调整策略，完整公开基准用于回归；不要根据已经查看的测试答案反复调参后宣称泛化提升。
2. 优先验证查询改写/词形归一化、跨会话证据汇集、段落排序与继续读取策略。每项改动都保持相同上下文预算测增益，避免仅靠塞入更多文本提高文件命中率。
3. 加入固定回答模型和官方评审流程，测最终回答、知识更新和拒答。到这一层再用同一套流程与一个候选后端作对照。
4. 以 LongMemEval-V2 和自有中文截图用例补齐 OCR、记忆生成、来源、事件时间和状态变化评测。

这轮原始对话没有 Wiki Link，也没有图扩展实验，所以不能用它判断 Wiki Link 或图数据库的收益。当前结果更适合决定先改善哪一段检索流程，而非立即替换整个记忆后端。
