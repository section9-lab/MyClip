# Memory 向量检索方案（2026-09-23）

状态：**已停止**（2026-09-24）。阶段 0 离线验证未达到 LoCoMo 门槛（结果见第十节），按决定不做向量检索；方案保留供日后参考。前序：[召回改造方案](memory-recall-redesign-2026-09-23.md)、[召回改造评测](../benchmark/docs/memory-recall-benchmark-2026-09-23.md)。

## 一句话

在现有 BM25 + Wikilink 图检索旁边加一路本地多语言向量检索，按 OpenClaw 的做法做向量 / 关键词加权融合；图传播的边权重同时参考事实行的向量相似度。模型首次使用时后台下载，不可用时自动退回纯关键词检索。不新增设置项，MCP 接口不变，继续支持 macOS 13。先用一天做离线验证，达到门槛再集成。

## 一、为什么要做

召回改造之后，单跳和跨会话汇总有提升，多跳没有。原因是词汇不重合（LoCoMo，按题型统计）：

| 题型 | 每条证据都与问题共享实词的题 | 当前 all@5（原始语料） |
|---|---:|---:|
| 单跳 | 78.6% | 96.4% |
| 时间 | 70.7% | 88.2% |
| 多跳 | 29.0% | 34.4% |
| 开放域 | 25.0% | 47.8% |

“实词”指去掉停用词和大写人名后的词。多跳题中 71% 至少有一条证据和问题没有任何共同的词（问“去过哪些国家”，证据写“在努克住了几天”）。BM25 与按 BM25 加权的图传播都只认字面；整理出的事实行是对原话的改写，也不贴近问题的用词。这部分只能靠语义匹配。

MyClip 自身的场景还多一层：截图 OCR 常是英文，提问常用中文，现在的关键词检索在跨语言时基本召回不到，只能靠人名、别名这类共同字面。多语言共享向量空间可以直接覆盖。

## 二、参考 OpenClaw

| 项 | OpenClaw | MyClip 采用 |
|---|---|---|
| 融合 | 向量与 BM25 两路并行，加权合并，默认向量 0.7、关键词 0.3 | 同样两路；权重在开发集上用严格口径确定，起点 0.7 / 0.3 |
| 本地模型 | llama.cpp 运行 `embeddinggemma-300m-qat-Q8_0.gguf`（约 0.3 GB，自动下载） | Core ML 运行，候选见第三节 |
| 任务前缀 | 其 issue #140932：本地提供方漏掉 EmbeddingGemma 的查询 / 文档前缀，recall@1 从 23/25 降到 16/25 | 按模型要求固定加前缀，并有单元测试 |
| 切块 | 400 token，重叠 80 | 复用现有段落；超过 400 token 的段落按 400 / 80 切窗 |
| 缓存 | 块向量缓存在 SQLite，内容不变不重算 | 按（模型、文本哈希）缓存，放在资料库外的共享缓存里 |
| 降级 | `provider: "none"` 时只用关键词 | 模型未就绪或出错时只用关键词，后台自动重试 |

## 三、模型选型

| 候选 | 参数 | 维度 | 最长输入 | 许可 | 前缀 | Mac 上运行 |
|---|---:|---:|---:|---|---|---|
| multilingual-e5-small | 118M | 384 | 512 token | MIT | `query: ` / `passage: ` | BERT 结构，可转 Core ML 并在神经网络引擎上用 float16 |
| EmbeddingGemma-300M | 300M | 768（可截到 512 / 256 / 128） | 2048 token | Gemma 条款（需接受） | `task: search result \| query: ` / `title: none \| text: ` | 官方说明激活值不支持 float16，神经网络引擎不适用，只能在 CPU / GPU 上用 float32 |
| Qwen3-Embedding-0.6B | 0.6B | 1024（可截断） | 32K token | Apache 2.0 | 查询端带指令 | 体积与计算量最大 |

三者都支持 100 种以上语言、中英文共享向量空间。**产品默认倾向 multilingual-e5-small**：许可最宽、体积最小（float16 约 240 MB，int8 约 120 MB）、能在神经网络引擎上跑。EmbeddingGemma 是 OpenClaw 的默认选择，但 float16 限制和许可条款都要额外处理。最终由第八节的离线验证按数据选定。

## 四、运行时

- **推理**：模型转换为 Core ML ML Program（macOS 12 起支持，满足 macOS 13 的最低版本要求），`computeUnits = .all`。分词器用 Hugging Face swift-transformers 的 Tokenizers，读取模型自带的 `tokenizer.json`；集成前确认其最低系统版本。
- **下载**：首次需要时从 MyClip 控制的地址下载模型包到 `~/Library/Application Support/MyClip/Models/<模型>/<版本>/`，校验 SHA-256 后原子替换。失败按现有重试策略退避重试，不弹窗、不要求用户操作。下载前检查磁盘空间，不足时维持纯关键词检索。
- **生命周期**：模型按需加载，空闲一段时间后释放内存；索引任务以低优先级（utility）在后台批量运行，每批 32 段，App 退出时可中断、下次继续。
- **确定性**：不同计算单元的浮点误差可能让得分并列的结果换序。检索结果按（分数、路径、段落序号）稳定排序；测试固定在 CPU 上运行。

## 五、索引

- **向量化的内容**：
  - 段落：`memory_passages` 的每一段，加文档前缀；长段落按 400 / 80 token 切窗，取窗口向量的最大相似度作为段落分数。
  - 事实行：`memory_links.fact`（边的那一行），供图传播使用。
- **存储**：资料库内新增派生表 `memory_vectors(entry_id, ordinal, window, kind, text_hash, vector)`，向量存 float16，随文件同步增删；共享缓存 `Embeddings.sqlite(model, text_hash, vector)` 放在资料库外，重建索引、换资料库或跑评测时，相同文本不重算。
- **规模估算**：以 5 万段、384 维为例，float16 存储约 38 MB；在内存中暴力计算余弦相似度约 1900 万次乘加，用 Accelerate 在毫秒级完成，不需要近似最近邻索引。
- **换模型**：模型版本写入表中，版本变化时后台重算，重算完成前继续用旧向量或纯关键词。

## 六、检索融合

在 `memory_search` 现有流程上改三处，接口不变：

1. **种子**：候选 = 关键词候选 ∪ 向量相似度前 50 段所属的页面（同样经过时间、应用与归档过滤）。页面的向量分 = 最佳三段相似度按 1、0.5、0.25 衰减求和，与关键词分分别归一化后加权：`lexical = 0.7 × 向量 + 0.3 × 关键词`（起点值，开发集调参）。标题与别名完全匹配的档位加分保持不变。
2. **图传播**：边的相关度由“事实行的 BM25”改为 `max(BM25 归一化, 事实行与问题的余弦相似度归一化)`。问题说“国家”、事实行写“去了努克”时，边能被语义点亮，桥接才真正起作用。
3. **片段**：段落按融合分排序；行的得分在 IDF 加权命中之外，加上该行作为事实行时的向量相似度。只靠向量命中、没有任何共同词的段落，取其开头几行。

融合后仍是“0.6 × 字面相关度 + 0.4 × 图传播”，只是“字面相关度”换成了上面的融合分。

## 七、预期收益

以下是估计，依据列在最后一列；第八节的离线验证会在集成前给出实测值。

| 指标（严格口径） | 当前 | 预期 | 依据 |
|---|---:|---:|---|
| LoCoMo 多跳 all@5（原始语料） | 34.4% | 40%–48% | 71% 的多跳题有字面不可达的证据；86% 的多跳题全部证据已在前 20 名内（排序空间充足）；同类方案中 MemPalace 在 LoCoMo 上 raw → hybrid 的会话 R@10 为 60.3% → 88.9%（口径不同，只作方向参考） |
| LoCoMo 开放域 all@5 | 47.8% | 52%–58% | 字面可达只有 25%，向量受益面最大，但这类题常需推理，检索提升有限 |
| LoCoMo 总体 all@5 | 80.5% | 82%–85% | 单跳、时间已在 88%–96%，主要增量来自多跳与开放域 |
| LongMemEval 总体 all@5 | 86.6% | 88%–91% | 采用向量与图的 Sibyl 在同口径 Recall@5 上比 MyClip 高 5.3 个百分点，差距集中在偏好、跨会话、时间三类 |
| LongMemEval 跨会话 all@5 | 75.2% | 78%–84% | 同上 |
| 中文提问、英文资料（MyClip 实际场景） | 基本召回不到（只能靠人名、别名等共同字面） | 可召回 | 多语言共享向量空间；公开评测测不到，需要用真实资料库建小型中文开发集 |
| 查询延迟 | — | 增加约 20–50 ms | 一次查询向量化加暴力检索 |
| 返回字数 | — | 不变 | 片段预算不变（2 段 × 300 字） |

不会改善的部分：需要跨多条证据做计数、比较、推理的问题，检索送达证据后仍要靠阅读模型；需要 4 个以上证据会话的聚合题，前 5 名装不下，仍需 Agent 用 `memory_get` 读实体页。

## 八、验证与门槛

**阶段 0：离线验证（约 1 天，不改产品代码）**

- 用 Python（sentence-transformers）加载 2–3 个候选模型，在 LoCoMo 与 LongMemEval 上做两组实验：
  1. **重排下界**：只对当前前 20 名按融合分重排，测严格口径 all@5；不需要改检索层就能估计收益。
  2. **完整融合**：对全部段落算向量，模拟第六节的融合，测召回能否超出前 20 名。
- 按对话 00–04 调融合权重，05–09 只跑一次；LongMemEval 看回归。
- **进入集成的门槛**（测试集）：多跳严格口径 all@5 至少 +6 个百分点；单跳、时间不下降超过 1 个百分点；LongMemEval 总体不下降。达不到就停止，不集成。

## 十、阶段 0 结果（2026-09-24）

用 `benchmark/vector.py` 在 Python 中验证：关键词一路直接取当前 `myclip-mcp`（2 段 × 300 字版本）的逐题前 20 名，向量一路用 multilingual-e5-small（`query: ` / `passage: ` 前缀，GPU 上约每秒 1,300 段）对同一语料的全部段落编码，页面分取最佳三段按 1 / 0.5 / 0.25 衰减求和，两路分数归一化后加权。计分为原始语料上的文件级 all@5（与评测报告的 ① ③ 同口径）。环境在 `benchmark/cache/venv`（1.0 GB），模型缓存在 `benchmark/cache/hf`（471 MB），均不进 Git。

**门槛判定**：LoCoMo 测试集多跳要求 +6 个百分点，实测 −0.7（融合 0.3）到 −1.4（融合 0.5），**未达到**；LongMemEval 不下降的要求达到，且明显上升。

**为什么两个数据集表现相反**

- 向量确实补上了一部分字面不可达的证据：LoCoMo 开发集的多跳证据中，与问题没有共同实词的 195 条，关键词排进前 5 的占 40%，向量占 48%；但与问题有共同词的 207 条，关键词 69%、向量 64%。多跳要求全部证据同时进前 5，两者相抵后题目层面几乎不变。
- LoCoMo 的会话全是同样两个人的生活闲聊，话题高度重叠：同一语料内会话向量的平均两两余弦相似度为 0.985，LongMemEval 为 0.924。会话在语义上几乎无法区分，排序只能靠具体的词，向量权重越高，单跳退步越多（融合 0.7 时单跳 +7 / −28）。
- LongMemEval 的每个会话话题各不相同，干扰会话来自无关对话，按语义就能区分出相关会话，跨会话题受益最大。

**对 MyClip 的含义**：真实资料库的 Daily 与项目页覆盖不同应用、项目和话题，更接近 LongMemEval 的“话题各异”；再加上中文提问、英文 OCR 的跨语言场景，公开评测都测不到。LoCoMo 的结果说明向量权重不能高：融合 0.3 在 LoCoMo 两个划分上合计 +27 / −15，在 LongMemEval 上 +14 / −0，是目前最稳妥的点。

**可选的下一步**

1. 按融合 0.3 进入集成（阶段 1–4），把门槛改为“LoCoMo 不退步、LongMemEval 提升”；预期 LongMemEval all@5 约 +3 个百分点、跨会话约 +6.6，LoCoMo 持平。
2. 先离线试更强的模型（Qwen3-Embedding-0.6B，约 1.2 GB 下载），看 LoCoMo 单跳是否也能不退步、多跳能否提升；产品侧的模型体积与计算量会明显变大。
3. 用真实资料库建一个小型中文开发集，测跨语言场景；涉及个人资料，需要用户同意。
4. 按原门槛停止向量方向。
