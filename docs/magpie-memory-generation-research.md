# Magpie 与桌面订阅账号的 ACP 记忆生成

实现进展：2026-10-25 已完成 MyClip 自有接入及两个产品的真实账号首次生成、增量编辑验证，详见 [实现与实测记录](desktop-acp-memory-generation.md)。以下保留 2026-10-24 的原始调研过程，不能将当时的“未完成”当作当前状态。

调研日期：2026-10-24。目标是复用千问办公、WorkBuddy 桌面端使用的产品账号和额度，通过 ACP 处理图片、文本及本地 Markdown。MCP 召回不属于本次链路。

## 实现边界（用户澄清）

用户明确要求参考 Magpie 的实现方案，不使用 Magpie。生产接入应由 MyClip 自己实现：不要求安装或运行 Magpie，不调用其本地网关，不安装其插件，不读取其账号存储。前面的本地网关探测仅为调研证据，不是产品依赖或接入方案。

参考范围包括账号授权与刷新、产品模型目录和能力发现、图文消息及工具调用的协议转换、流式错误和用量处理。实际适配代码由 MyClip 维护；如复用 MIT 代码片段，需要保留许可及来源、审核并去除与需求无关的行为。优先复用项目现有网络、钥匙串及 ACP 能力。

## 结论

可借鉴的实现是分离执行器与模型账号：MyClip 经 ACP 驱动执行器，由 MyClip 自己维护的账号与协议适配层连接同一产品账号的模型；工具仍在执行器中实际运行，执行结果回传模型，最终写入 MyClip Memory。账号授权可与桌面会话分开，但必须核对为同一账号、同一额度来源。若引擎需要兼容 HTTP 接口，该接口也由 MyClip 自己提供并管理生命周期，不连接 Magpie。

这提供了可验证的候选路线，不能据此声称已经接通原桌面 Agent 的会话、宿主工具或插件。优先复用已经工作的 OpenCode 执行器验证账号路线，再分别验证千问办公内置 ACP 引擎、WorkBuddy 官方 ACP 引擎是否支持该模型配置。界面应明确显示执行器、账号来源及动态模型目录。

## WorkBuddy

社区插件支持同一产品的浏览器授权、账号模型目录、工具请求及额度查询。桌面登录复用模式逐次只读桌面文件；插件明确说明 WorkBuddy 5.6 及以后凭据加密，该模式不能读取，需浏览器重新授权。本机为 5.9.0，因此不能承诺零操作复用现有桌面会话；同一账号重新授权后是否使用同一额度仍需实测确认。

Magpie 的 `internal/agent/workbuddy.go` 是将网关模型写入 WorkBuddy 自定义模型目录，并非通过 ACP 遥控桌面。它与订阅账号提供方是两个方向的适配，不可混淆。

当前插件有处理上游“未获批准渠道”拒绝的身份改写和重试逻辑。本项目不直接安装或移植这部分行为；若服务端明确拒绝渠道，应保留失败状态和原因。可借鉴账号授权、刷新串行化、模型能力映射和错误处理。

## 千问办公

已找到非官方、未经 Magpie 审核的 `opencode-qwenwork-auth` 插件，版本 0.1.0。其代码使用千问办公设备授权流程，查询账号的 `qwork` 模型目录及套餐额度，将宿主工具请求转换为产品的流式生成协议，并把工具调用映射回来。图片输入转换存在于适配器代码中，模型图像能力来自上游 `is_vl`。

这与单独使用 Qwen Code 或 DashScope 账号不同，但插件作者对旧版桌面的验证声明不等于本机 1.3.2 已验证。当前配置的初始模型目录为空；上游目录读取失败时会退回已有目录，因此 MyClip 必须区分实时、缓存和失败，不能将缓存当作新读取成功。

## MyClip 接入与验收要求

1. 复用现有 ACPClient 和执行器工具循环；新增独立的账号/模型来源配置，由 MyClip 直接实现千问办公与 WorkBuddy 的授权、动态目录及协议适配，不依赖 Magpie 网关或插件。复用现有网络和钥匙串实现，不另建重复基础设施。
2. 从已授权账号动态取得模型及图片、工具能力；不预置型号清单。模型目录读取失败应显示错误或缓存状态，不能静默改用其他付费提供方。
3. 对图片记忆任务只允许支持图片及工具调用的模型；不支持时给出可操作错误。执行器仍须真实返回读文件、编辑、命令等事件。
4. 使用同一账号完成授权后，核对账号身份、套餐、额度来源。登录失效、额度不足、渠道拒绝均记为实际失败，不以正常流结束冒充成功。
5. 使用隔离资料库和只有图片中包含的随机事实，验证 ACP 发送图文、工具循环、Markdown 新增/修改、来源关联及入库；同时核对产品侧用量。两个主要账号分别验收。
